# `migrations/` — migracje Doctrine

Przeczytaj ten plik **przed** dodaniem migracji.

## Za co odpowiada

Wykonanie schematu opisanego w `docs/database.md`. Ten dokument jest projektem, migracje są
jego wykonaniem. Jeśli się rozjadą, źródłem prawdy jest baza, a `docs/database.md` jest
defektem do naprawy — nigdy odwrotnie „po cichu”.

## Decyzje lokalne, których nie wolno cofnąć

1. **Surowy SQL przez `addSql()`, nigdy `$schema->createTable()`.** Schemat używa rzeczy,
   których abstrakcja DBAL nie wyraża: `GENERATED ALWAYS AS IDENTITY`, indeksów częściowych,
   `CREATE CONSTRAINT TRIGGER … DEFERRABLE INITIALLY DEFERRED`, nazwanych `CHECK`.
2. **`doctrine:migrations:generate`, nigdy `diff`.** Od ADR 0018 w projekcie **jest** ORM
   i są encje (`src/Entity`), więc `diff` ma z czego liczyć różnicę — i właśnie dlatego jest
   groźniejszy niż wcześniej: liczy ją z metadanych, które są **z założenia niepełne**.
   Mapowanie nie wyraża 30 ograniczeń `CHECK`, 4 wyzwalaczy, 4 funkcji PL/pgSQL ani kolumn
   `GENERATED ALWAYS AS IDENTITY`, więc wygenerowana migracja proponuje skasowanie tego, czego
   nie widzi, i przestawienie kluczy głównych na `GENERATED BY DEFAULT`. Poprawny obieg jest
   niezmieniony: `generate` tworzy pusty szkielet, SQL wpisuje się ręcznie z `docs/database.md`.
   `diff` wolno uruchomić **wyłącznie po to, żeby obejrzeć różnicę** — jego wynik nigdy nie
   trafia do commita. `doctrine:schema:update` i `doctrine:schema:create` są zakazane; ten drugi
   dodatkowo dlatego, że mapowanie deklaruje wartości domyślne jako literały tekstowe
   (`docs/orm.md` §6) i wygenerowałby błędny `DEFAULT`. Makefile już to odzwierciedla.
2a. **Po każdej zmianie schematu sprawdź mapowanie.** Migracja i encje muszą się zgadzać:
   `doctrine:schema:validate --skip-sync` plus test porównujący różnicę z listą pięciu znanych
   instrukcji (`docs/orm.md` §9). Kontrola **nie wykryje** skasowanego `CHECK`, wyzwalacza ani
   funkcji — te pilnują testy zachowania z `docs/database.md` §12. Migracja dotykająca wyzwalacza
   albo `CHECK` bez odpowiadającego testu jest defektem blokującym.
2b. **Nowy indeks trzeba zadeklarować także w encji**, tą samą nazwą. Inaczej kontrola z 2a
   zgłosi go jako `DROP INDEX`.
3. **Każda migracja zaczyna się od `SET lock_timeout = '3s'`.** `ALTER TABLE` czeka na
   `ACCESS EXCLUSIVE` i **blokuje za sobą wszystkie odczyty**, także te, które tej blokady nie
   potrzebują. Bez limitu jedno długie zapytanie zatrzymuje całe API.
4. **Migracje nie uruchamiają się przy starcie kontenera.** Osobne zadanie ECS, raz, przed
   przełączeniem ruchu. Trzy zadania startujące równolegle wyścigowałyby się o tę samą migrację.
5. **Migracja nieodwracalna bez utraty danych ma `down()` rzucający wyjątek**, a nie udający,
   że cofnie.

## Reguły dla zapełnionej tabeli

Pełna tabela operacji i bezpiecznych sposobów jest w **`docs/database.md` §9**. Skrót
najczęstszych pomyłek:

| Chcesz | Zrób |
|---|---|
| nowa kolumna | `ADD COLUMN … NULL` — metadane, bez przepisania (PostgreSQL 11+) |
| nowy `CHECK` | `ADD CONSTRAINT … NOT VALID`, potem osobno `VALIDATE CONSTRAINT` |
| rozszerzyć słownik `gearbox`/`drive`/`status` | `DROP CONSTRAINT` + `ADD … NOT VALID` + `VALIDATE` |
| nowy indeks | `CREATE INDEX CONCURRENTLY` **i** `isTransactional(): bool { return false; }` |
| `NOT NULL` na istniejącej kolumnie | `CHECK … NOT VALID` → `VALIDATE` → `SET NOT NULL` → `DROP CONSTRAINT` |
| usunąć / przemianować kolumnę | dwa wdrożenia (rozszerz-i-zwęź), nigdy jedno |
| zmienić typ kolumny | nowa kolumna + podwójny zapis + przepisanie partiami + zamiana |

## Pułapki

1. **`CREATE INDEX CONCURRENTLY` nie działa w transakcji.** Bez nadpisania `isTransactional()`
   migracja wywali się na `CREATE INDEX CONCURRENTLY cannot run inside a transaction block`.
   Po nieudanym przebiegu zostaje indeks `INVALID` — sprawdź `pg_index.indisvalid`, usuń go
   `DROP INDEX CONCURRENTLY` i powtórz.
2. **Kolejność `DROP` w `down()` jest odwrotna do `up()`** i musi respektować `RESTRICT`:
   warianty → wersje → modele → marki → przebiegi. Wyzwalacze i funkcje przed tabelami.
3. **Ciało funkcji PL/pgSQL zawiera średniki.** Każde `CREATE FUNCTION` musi być **jednym**
   wywołaniem `addSql()`; nie próbuj rozbijać go po średnikach.
3a. **Wyzwalacz `TRUNCATE` nie może być `CONSTRAINT TRIGGER`.** `CREATE CONSTRAINT TRIGGER`
   przyjmuje tylko `INSERT`/`UPDATE`/`DELETE`. Wyzwalacz na `TRUNCATE` jest zwykły, `AFTER`
   i `FOR EACH STATEMENT`. Kolejność `DROP` w `down()` musi to uwzględniać — cztery wyzwalacze
   i cztery funkcje, w tym wspólna `version_must_keep_variant(BIGINT)` kasowana z sygnaturą.
4. **`gen_random_uuid()` jest w rdzeniu PostgreSQL od wersji 13.** Nie dodawaj
   `CREATE EXTENSION pgcrypto` — jest zbędne.
5. **Nowa migracja to nowy plik.** Nigdy nie edytuj migracji, która została wykonana na
   jakiejkolwiek bazie poza lokalną. Wyjątek dotyczył wyłącznie okresu przed pierwszym
   wdrożeniem: `fuel_type` i `unresolved_segment` zostały dopisane wprost do
   `Version20260902100000`, żeby pierwsze wydanie nie zaczynało się od migracji poprawiającej
   migrację. Od pierwszego wdrożenia ta furtka jest zamknięta.
6. **Widok materializowany nie jest tabelą i DBAL go nie introspekuje.** Nie wymaga wpisu
   w `schema_filter`, nie pojawia się w kontroli z 2a i nie potrzebuje encji. Sprawdzone po
   dodaniu `variant_search` i `search_term`: `doctrine:schema:update --dump-sql` zwraca te same
   pięć instrukcji, co wcześniej. Nie „napraw" tego dopisując je do `schema_filter`.
7. **`REFRESH MATERIALIZED VIEW CONCURRENTLY` wymaga indeksu unikalnego i widoku zapełnionego**,
   i nie działa w transakcji. Dlatego oba widoki powstają `WITH DATA` i oba dostają indeks
   unikalny w tej samej migracji. Widok utworzony `WITH NO DATA` wywróci pierwsze odświeżenie.
8. **Nie twórz tu migracji dla tabeli należącej do adaptera bez nazwania jej po adapterze.**
   `autocentrum_page_cache` nazywa się tak celowo — po podmianie źródła ma być oczywiste,
   co usunąć.
